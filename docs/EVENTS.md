# pgsql_api: требования и event layer

Документ собирает в одном месте всё, что решено про pgsql_api, и описывает слой событий
(near real-time уведомления для CRM, CMS, Nextcloud и других клиентов).

Источники:

- обсуждения 29.11.2025 и 28.12.2025 (философия API), 14.04.2026, 22.04.2026, 19.07.2026 —
  восстановлены по пересказу ChatGPT, исходные чаты не проверялись;
- обсуждение 09.11.2026 (Claude): опрос + «пушер» на Rust, курсор, права;
- аудит кода `main` @ `7d25baa`.

---

## 1. Три независимые части

| Часть | Что делает | Чего НЕ делает |
|---|---|---|
| **pgsql_api** (`pgsql.php`, `pgsql.js`) | транспорт SQL, сессии, роли, выдача токена для ленты | бизнес-логика, ACL, постоянные соединения |
| **Event layer** (`sql/notify.sql`, `notifyd/`) | сообщает «что, где и когда изменилось» | не передаёт содержимое строк, не решает о правах сам |
| **Прикладные системы** (CRM, CMS, Previous Ground, Nextcloud…) | используют обе части | не встраиваются в pgsql.php |

Правило: API не дублирует PostgreSQL. Права определяют только `GRANT`, RLS, CLS и роли.

## 2. Реестр требований

Статусы: **есть** — реализовано и проверено тестом; **частично**; **нет**; **вне** — не задача этого репозитория.

| # | Требование | Статус |
|---|---|---|
| A1 | Два основных файла: `pgsql.php` и `pgsql.js` | есть |
| A2 | Минимальный транспорт JS → PHP → PostgreSQL | есть |
| A3 | Без бизнес-логики и ACL в PHP | есть |

## 3. Как работает event layer

```
 пользователь меняет строку (через pgsql_api или любым другим путём)
        │
        ▼
 ┌──────────────── PostgreSQL ────────────────┐
 │ crm.customer ──trigger notify.capture()──┐ │
 │                                          ▼ │
 │ notify.registry  (что отслеживаем)   notify.event (журнал)
 │                                          │ │
 │                    pg_notify('notify_event', '')  — один сигнал на транзакцию
 └──────────────────────────────────────────┼─┘
                                            │ одна LISTEN-связь
                                            ▼
                                     ┌─────────────┐  в памяти: последние N событий
                                     │   notifyd   │──► вебхуки (CRM, CMS, адаптер Talk…)
                                     │   (Rust)    │
                                     └──┬───────┬──┘
                  GET /events?cursor=…  │       │  GET /stream (SSE)
                  каждые ~30 с (правда) │       │  «hint» сразу (подсказка)
                                        ▼       ▼
                                   10 000 браузеров
                                        │
                                        └──► pgsql.php query(...) — перечитать данные своей ролью
```

Две дороги к клиенту устроены по-разному.

- **Опрос — источник правды.** Клиент спрашивает «что было с курсора C». Если SSE-сообщение
  потерялось, клиент всё равно узнает об изменении, самое позднее через ~30 с.
- **SSE — только подсказка.** Сообщение содержит лишь `{"cursor":"…"}`, и клиент сразу делает опрос.
  Потерянная или лишняя подсказка ничего не ломает.

Клиенты не держат соединений с БД. У демона ровно одно соединение, сколько бы ни было клиентов.
Опрос демон обслуживает из памяти, без запроса к БД.

## 4. Две таблицы

### 4.1 `notify.registry` — что отслеживаем

Одна строка на таблицу. Сюда регистрируются все объекты, изменения которых должны попасть в ленту.

| Столбец | Смысл |
|---|---|
| `table_oid` | отслеживаемая таблица |
| `topic` | логическое имя, например `crm.customer`, `deck.card` |
| `pk_columns` | первичный ключ, берётся из каталога автоматически |
| `scope_column` | столбец для маршрутизации и прав (`tenant_id`, `board_id`…); его значение попадает в событие как `scope` |
| `watch_columns` | UPDATE создаёт событие, только если изменился один из этих столбцов; `null` — любой |
| `ops` | какие операции отслеживать (`INSERT`, `UPDATE`, `DELETE`) |
| `enabled` | временно выключить, не удаляя |

Регистрация — одной функцией, триггер создаётся сам:

```sql
select notify.register('crm.customer', 'crm.customer',
                       p_scope_column  => 'tenant_id',
                       p_watch_columns => array['name', 'note']);   -- updated_at не шумит

select notify.unregister('crm.customer');
```

### 4.2 `notify.event` — куда собираем

Журнал изменений. Хранит только «что, где и когда», **без содержимого строк**.

| Столбец | Пример |
|---|---|
| `id` | 4711 |
| `xid` | xid транзакции, нужен для курсора (см. §5) |
| `ts` | время транзакции |
| `topic`, `scope` | `crm.customer`, `1` |
| `table_name` | `crm.customer` |
| `op` | `INSERT` / `UPDATE` / `DELETE` |
| `pk` | `{"id": 123}` |
| `changed_columns` | только для UPDATE: `{note}` |

Писать в журнал может только триггер (`security definer`). У прикладных ролей нет доступа к `notify.event`,
у роли `notify_daemon` — только чтение. Очистка по сроку хранения: `notify.purge(interval)`, её вызывает
демон раз в 10 минут.

Одинаковые `NOTIFY` в одной транзакции PostgreSQL схлопывает, поэтому массовый `UPDATE` на 10 000 строк
даёт демону один сигнал, а не 10 000.

## 5. Курсор: почему не `id > last_id`

Идентификаторы выдаются при вставке, а коммиты идут в другом порядке. Если транзакция A получила
`id = 5`, а транзакция B — `id = 6` и закоммитилась раньше, клиент с курсором `id > 4` увидит 6,
сдвинет курсор и **навсегда пропустит** 5.

Поэтому курсор — это **горизонт**: `xmin` текущего снимка (`notify.horizon()`). Все транзакции с
`xid` ниже горизонта завершены, значит набор событий ниже него окончателен. Клиент получает события
из `[курсор, горизонт)`, новый курсор равен горизонту.

Это проверено тестом: событие из быстрой транзакции ждёт, пока закоммитится более старая открытая,
и потом оба приходят вместе.

Цена: долгая **пишущая** транзакция в кластере задерживает ленту до своего завершения. Чтение
(отчёты, `pg_dump`) не задерживает, у него нет xid. Рекомендуется `idle_in_transaction_session_timeout`.

## 6. Права в ленте

Что клиенту разрешено видеть, решает БД. При выдаче токена `pgsql.php` вызывает `notify.claims()`
**от имени пользователя** (после `SET ROLE`), и результат подписывается в токен.

- По умолчанию topic разрешён, если у текущей роли есть `SELECT` на таблицу (все scope).
- Приложение может заменить функцию и выдавать точные scope:

```sql
create or replace function notify.claims() returns jsonb
language sql stable security invoker set search_path = pg_catalog, notify as $$
    select jsonb_build_object('crm.customer',
        coalesce((select jsonb_agg(tenant_id::text)
                  from crm.tenant_member where role = session_user), '[]'::jsonb))
$$;
```

Даже если лента скажет лишнее, данные защищены: клиент перечитывает их через API своей ролью, и RLS
решает, что он увидит.

## 7. Контракт

### pgsql.php: `event_token`

```json
→ {"action": "event_token"}
← {"data": {"token": "<HS256>", "url": "https://…/notifyd", "exp": 1767225600}}
```

Токен: `{aud, sub, role, topics: {"topic": null | ["scope", …]}, iat, exp}`, HS256, общий секрет с демоном.

### notifyd: `GET /events?cursor=C[&limit=N]`

Заголовок `Authorization: Bearer <token>` (или `?token=`).

```json
{"cursor": "1834", "more": false, "reset": false,
 "events": [{"id": 4711, "ts": "2026-11-09T19:40:01.2+01:00", "topic": "crm.customer",
             "scope": "1", "table": "crm.customer", "op": "UPDATE",
             "pk": {"id": 123}, "changed": ["note"]}]}
```

- без `cursor` — текущий горизонт и пустой список (новый клиент);
- `more: true` — сразу запросить ещё раз с новым курсором;
- `reset: true` — курсор старше срока хранения (или от другой базы): перезагрузить данные целиком.

### notifyd: `GET /stream` (SSE)

`event: hint` / `data: {"cursor":"1834"}` — только когда есть события, видимые этому клиенту.
`event: expired` — токен истёк, клиент берёт новый и переподключается. Keep-alive каждые 25 с.

### notifyd: `GET /health`

### Вебхуки

`NOTIFYD_WEBHOOKS=/etc/notifyd/webhooks.json`:

```json
[{"name": "crm-sync", "url": "https://crm.local/hooks/pg", "topics": {"crm.customer": null}, "secret": "…"}]
```

POST с телом как у `/events`, заголовок `X-Notifyd-Signature: sha256=<hex hmac>`. Доставка в порядке
очереди, 3 попытки. Кому важна гарантия — опрашивает `/events` своим курсором.

Nextcloud Talk ждёт свой формат сообщений и подписи бота, поэтому общий вебхук напрямую в Talk не
подходит. Нужен маленький адаптер. Это следующий шаг, см. §10.

## 8. Клиент (`pgsql.js`)

```js
const db = createPgsql();
await db.connect("crm", user, password);

const feed = db.events({
  interval: 30000,                         // опрос, со случайным разбросом ±20 %
  onEvents: (events) => {                  // только «что/где/когда»
    for (const e of events) {
      if (e.topic === "crm.customer") refreshCustomer(e.pk.id, e.op);
    }
  },
  onReset: () => reloadEverything(),
});
await feed.start();     // сначала курсор…
await loadInitialData(); // …потом данные: изменения в промежутке придут событиями
```

`refreshCustomer` перечитывает строку обычным `db.query(..., { params: [id] })`. Для `DELETE` строку
перечитывать не нужно, её просто убирают из UI.

## 9. Развёртывание

```bash
psql -d crm -f sql/notify.sql                     # от владельца схемы
psql -d crm -c "alter role notify_daemon password '…'"
psql -d crm -c "select notify.register('crm.customer', 'crm.customer', 'tenant_id')"

cd notifyd && cargo build --release               # → target/release/notifyd
```

- **PHP:** `PGSQL_EVENT_SECRET` в окружении php-fpm (или `$pgsql_events['secret']` в конфиге); в профиле
  `events_url` (URL демона для браузера) и при необходимости `events_aud`.
- **Демон:** `notifyd/notifyd.service`. Переменные: `NOTIFYD_DATABASE_URL`, `NOTIFYD_SECRET`, `NOTIFYD_AUD`;
  необязательные `NOTIFYD_LISTEN` (127.0.0.1:8090), `NOTIFYD_BUFFER` (50000), `NOTIFYD_RETENTION_SECS` (86400),
  `NOTIFYD_TICK_MS` (1000), `NOTIFYD_CORS_ORIGINS`, `NOTIFYD_WEBHOOKS`.
- **nginx** (тот же origin, тогда CORS не нужен):

```nginx
location /notifyd/ {
    proxy_pass http://127.0.0.1:8090/;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_buffering off;            # иначе SSE копится в буфере
    proxy_read_timeout 1h;
}
```

- 10 000 SSE-клиентов = 10 000 сокетов: `LimitNOFILE` и `worker_connections` в nginx.
- Демон подключается без TLS (локальный TCP, решение для openSUSE/SELinux). Для удалённой БД нужен TLS-коннектор.
- Пароль БД лежит в PHP-сессии открытым текстом. Каталог сессий должен быть доступен только php-fpm.
  Улучшение: шифровать credentials ключом из отдельной cookie.
