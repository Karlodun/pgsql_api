# План развития репозитория: BTRFS‑менеджер для динамических пулов

Документ фиксирует целевую функциональность и поэтапный план доведения проекта до рабочего состояния для сценария: частые перестановки дисков, смешанные HDD/SSD уровни, несколько пулов с разными RAID, контроль снапшотов и проверка целостности.

## 1. Цели и принципы

- **Единая точка контроля** для всех машин/пулов (рабочая станция + серверы).
- **Наглядность**: визуальная карта пулов/дисков/уровней (горячее/тёплое/холодное).
- **Безопасность действий**: контрольные шаги при добавлении/удалении дисков, защита от ошибок выбора устройства.
- **Наблюдаемость**: метрики, состояние, журнал операций, уведомления.
- **Транзакционный UX**: сценарии “план → проверка → применить”, включая dry‑run.

## 2. Основные пользовательские сценарии

1. **Обзор инфраструктуры**
   - Список всех машин и пулов, ёмкость, уровень RAID, типы дисков.
   - Отображение “горячее/тёплое/холодное” на уровне пулов и устройств.

2. **Динамика состава пулов**
   - Добавление/удаление дисков.
   - Миграция между пулами.
   - Замена дисков на больший объём.

3. **Снапшоты**
   - Список снапшотов, политика ретенции, проверки “сделан/удалён”.
   - Дифф между снапшотами (вместе с оценкой объёма).

4. **Состояние и целостность**
   - Автоматические проверки scrub, balance, device stats.
   - Уведомления о деградации RAID или ошибках I/O.

## 3. Предлагаемая архитектура

### 3.0. Технологический выбор
- **Backend:** PHP (через существующий Nginx/Apache + PHP‑FPM).
- **Команды BTRFS:** выполнение через `sudo` с ограниченным набором разрешённых команд.
- **Frontend:** простой Web UI (SPA или статический HTML + JS), с табами и минимальным скроллом.

### 3.1. Агент на хосте (BTRFS Agent)
- Лёгкий сервис на PHP, который выполняет команды BTRFS и читает `/proc`, `/sys`, `btrfs fi show`, `btrfs filesystem usage`, `btrfs device stats`, `btrfs subvolume list`, `btrfs qgroup show`.
- Экспортирует данные в JSON через локальный API (HTTP на localhost или локальная сеть).
- Поддерживает dry‑run режим, если возможно (например, через анализ ожидаемых операций).

### 3.2. Централизованный API
- Собирает данные от агентов, хранит состояние, операции и историю.
- Асинхронная очередь задач: длительные операции (balance, scrub) не блокируют UI.
- Работает локально/по SSH‑туннелю, без публичного доступа.

### 3.3. Web‑интерфейс
- Дашборд с картой пулов и дисков.
- Мастер‑операции: “замена диска”, “добавить диск”, “расширить пул”.
- Конструктор политик снапшотов.
- Навигация по табам (без “обоев” и излишнего скролла): обзор → операции → снапшоты → настройки.

### 3.4. Аутентификация и sudo
- Доступ только из локальной сети/localhost; опционально только через SSH‑туннель.
- Вход с проверкой пароля (например, через PHP‑сессию).
- Команды выполняются через `sudo` с ограниченным `sudoers`‑листом.
- Политика “password cache”: допускается общий sudo‑кэш на ~10 минут, без расширения прав.

## 4. План работ (по этапам, без отдельного MVP)

### Этап 1. Инвентаризация и чтение состояния
- Сбор данных: список устройств, пулов, RAID, уровни, свободное место, ошибки.
- Отображение снапшотов и их политики.
- Структурированное логирование команд.
- Конфигурации на хосте: правила снапшотов и ретенция на каждом сервере.

**Результат:** статический мониторинг, без изменения состояния, как часть полноценной системы (без отдельного MVP).

### Этап 2. Безопасные операции изменения
- Добавление/удаление дисков с confirm‑шагами.
- Миграции между пулами (с прогнозом занятости и времени).
- Автоматические валидации: правильный диск, минимальный баланс.

**Результат:** базовый функционал управления.

### Этап 3. Политики и автоматизация
- Планировщик balance/scrub.
- Политики снапшотов: частота, ретенция, объём.
- Уведомления: деградации, ошибки чтения/записи.
- Конфиг‑таб для управления правилами (разные политики для разных машин).

**Результат:** автономное обслуживание.

### Этап 4. Оптимизация производительности
- Маркировка SSD/HDD и распределение данных по уровням.
- Аналитика горячих данных (hot/cold), рекомендации по миграции.
- Возможность автоматических миграций по политике.

**Результат:** поддержка “горячее/тёплое/холодное” хранилище.

## 5. Улучшения, которые закрывают текущие боли

- **Визуальный выбор диска**: исключаем ошибки “выбрал не тот диск”.
- **Dry‑run и прогноз**: оценка объёма, времени, рисков операции.
- **История действий**: кто/когда/что поменял.
- **Единый интерфейс для снапшотов**: статус, ретенция, дифф.
- **Табы вместо длинных страниц**: быстрые переключения между разделами.

## 6. Технические предложения

- Хранить описание инфраструктуры как декларативную модель (например, YAML), чтобы сравнивать “желаемое состояние” с “фактическим”.
- Для сложных действий использовать “план‑применить”, как в IaC.
- В API обеспечить идемпотентность операций.
- Централизованная база событий (audit log) для диагностики.
- Ограничить `sudo` до whitelist‑команд (`btrfs`, `mount`, `umount`, `lsblk`, `blkid`).

## 7. Риски и ограничения

- BTRFS операции долгие и ресурсоёмкие — нужна очередь и прогресс‑бар.
- Нужна строгая валидация устройств, особенно при hot‑swap.
- Поддержка нескольких версий BTRFS и разного поведения утилит.

## 9. Идея для следующего этапа: “BTRFS Zenbox”

Цель: быстрый подъём тестовых окружений (PostgreSQL/MySQL/веб‑сервисы) на основе read‑only снапшотов BTRFS.

- Создаём read‑only снапшот продакшн‑тома.
- Монтируем его в отдельную директорию как read‑write (через отдельный subvolume/loop‑mount, где требуется).
- Меняем порты/конфиги в копии и поднимаем сервис как отдельный инстанс.
- Быстрое удаление/сброс через удаление subvolume.

Рабочее название вкладки: **BTRFS Zenbox** (варианты: **Zenbox Instances**, **Sandbox Clones**).
